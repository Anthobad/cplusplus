# Security and assessment-integrity hardening

This revision is local and has not been deployed. It does not enable billing, create cloud services, change Vercel project settings, deploy Firestore rules, scan production learners, or configure service-account credentials. The live site retains its current rules until an approved rollout.

## Exact changes

`firestore.rules` now allows owners to read their user documents/history but denies every client create, update and delete under `/users/{uid}`. Shared `/exams/{examId}` remains readable to authenticated users and denies client writes, including clients with an `admin` claim. Shared exam publishing requires trusted server tooling with appropriate IAM credentials; there is no new public publishing endpoint. Internal quota, session and migration-marker collections remain inaccessible through client rules.

`server/security/firebaseAdmin.ts` pins authentication and database operations to the configured Firebase project and its existing named Firestore database. It verifies Firebase ID tokens using Admin SDK signature/audience/issuer validation and enables revoked-token/disabled-user checks. Production Vercel runtimes reject emulator trust configuration. Credentials stay server-side. Missing authentication returns 401; authentication/store configuration failures fail closed with 503. No development authentication bypass or in-memory production quota fallback was added. See Firebase's [ID-token verification guidance](https://firebase.google.com/docs/auth/admin/verify-id-tokens) and [Admin SDK/session guidance](https://firebase.google.com/docs/auth/admin/manage-sessions).

`server/security/progress.ts` supplies trusted progress operations. New coding verification comes only from a successful, registered, unassisted assessment result produced by the existing compiler evaluator. Practice passes retain their practice status. Optional interview-track challenges still do not affect curriculum progress. Lesson completion is checked against server-stored sequential/milestone prerequisites. The existing manual “Mark Complete” policy remains a learner declaration; completing a lesson still does not require a quiz or compiler pass. No new mastery gate is introduced.

Quizzes submit answer selections and are scored against the authored server question keys and existing thresholds. As before, only passing quiz results are saved. Exams use server-issued, owner-bound, randomized sessions with the existing eight-question composition, IDs, weights, pass threshold and duration displayed by the frontend. Submission accepts answers and session ID, not client totals, question sets or grading results. Server grading reuses the same compiler and explanation scoring functions. Validated partial results are saved privately with hashes of the answer and grading configuration, allowing retries after provider errors/function interruptions without awarding an incomplete attempt. Successful completion atomically saves the root progress, history record and idempotent session outcome. Replaying a completed session returns its original result instead of creating another attempt.

`server/security/routes.ts` exposes authenticated `/api/progress` reads, profile-only updates, quiz submission, explicit lesson completion/reset, and exam start/submit operations. Profile updates accept only display name and declared level. Caller-supplied UIDs, verified flags and scores cannot select the owner or update authoritative progress. Mock-interview reports are now validated and saved from the server-generated response; the browser no longer supplies report totals to Firestore or fabricates a default score when a report is absent.

The frontend sends Firebase bearer tokens through `authenticatedFetch`, using a shared anonymous-sign-in request when a guest first needs an API operation. Account changes during a request prevent its result from being applied to the newly selected account. Ordinary client Firestore progress writes are removed. Exam/quiz/lesson UIs await trusted results and retain answers on service failures. Local caches support display/history and cannot authorize server progression. Existing history reads include older documents without `completedAt`, rather than excluding them through an order-by query.

Because the application now holds administrative credentials, the public evaluation boundary also rejects `LocalCodeRunner` and obvious loopback/unspecified-host isolated-daemon endpoints before executing code. A host process limit is not credential isolation: student code could inspect the application filesystem/process environment. The existing Vercel Sandbox path is unchanged. Local API development must select a separate sandbox/provider, such as the existing Vercel Sandbox, Wandbox, or a separately isolated remote runner; the automatically started same-host development daemon cannot be used by the trusted API. Direct local compiler use remains available to authored regression tests. Remote runner endpoint/IAM/container isolation remains an operator responsibility.

## Distributed resource limits

`server/security/access.ts` uses Firestore transactions across a global and a UID-hashed user record, so counters/leases apply across Vercel instances and cold starts. Firebase documents [transactional atomicity and retries](https://firebase.google.com/docs/firestore/manage-data/transactions); these guards do not rely on process memory or caller-controlled forwarded IP headers.

| Execution work | Signed-in user | Anonymous user | Global |
| --- | ---: | ---: | ---: |
| Per UTC minute | 6 units | 3 units | 20 units |
| Per UTC day | 50 units | 10 units | 200 units |
| Concurrent leases | 1 | 1 | 2 |

Code evaluation, standalone explanation grading, mentor and mock-interview requests cost one execution unit. Exam submission reserves three units for its compiler/two explanation workload, including retries. Invalid requests and provider failures after reservation consume quota; there is no refund path to exploit. Successful idempotent replay still consumes its reservation. Fixed-minute windows can allow a burst across a minute boundary; the concurrency and daily guards still apply.

Progress/profile/quiz/reset/exam-start operations have a separate transactional action budget: 60/minute and 500/day per registered user, 30/minute and 200/day per anonymous user, 300/minute and 5,000/day globally, with at most four concurrent actions per user and twenty globally. Limits are fixed in source, not supplied by the client. New identities do not bypass global limits.

Leases last ten minutes and are released in a finally block. Release failures retain the occupied lease until expiry, and a killed function's lease expires without requiring a cron service. This conservative lifetime covers the existing 240-second function limit plus the bounded sandbox lifetime. A crash can temporarily reduce capacity for up to ten minutes. A 429 includes a `Retry-After: 60` hint; a daily limit needs the next UTC day, and a crashed lease may need longer. The quota store being unavailable prevents compiler/AI work.

Requests have a 256 kB JSON body limit, a 32,000-character code-answer limit, and a 12,000-character explanation limit. Successful reserved work can still consume existing Firestore, Vercel, sandbox and model usage. Limits are application guards, not a provider billing cap or a guarantee that a Firebase/Vercel allowance cannot be exhausted. No Redis plan, Cloud Function, scheduled job, TTL policy, billing upgrade or paid service was provisioned. Existing [Vercel duration/platform limits](https://vercel.com/docs/functions/limitations) continue to apply; interrupted exams can resume from server-validated partial results.

## Migration compatibility and approved rollout

The source/schema review and fixtures cover canonical, week and historical IDs, existing quiz/exam maps, verification lists and native Firestore timestamps. On first trusted access, an existing cloud root document is archived once at `/users/{uid}/legacySnapshots/pre-hardening`, normalized through the existing ID migration, and retained as the progression baseline. Unknown historical fields/subcollections are not deleted. A private `_integrity/{uidHash}` marker records migration; a previously client-writable `integrityVersion` field alone cannot bypass archival. New accounts start clean. Native Firestore field types are retained in the archive.

Existing cloud results were writable under the old rules. Keeping their IDs, history and progression cannot establish that those historical results were genuine. They are explicitly marked as a legacy baseline; only new operations are protected by this revision. Do not describe grandfathered `verifiedCodingPassed` entries as newly compiler-certified. Retroactive revalidation would be a separate policy decision that could change saved progression.

Existing browser caches and guest exam history are retained locally, with the old progress cache archived before replacing its displayed state with a trusted response. They are never uploaded as verified evidence. A guest with only old local progress and no corresponding cloud account cannot safely carry those claims into authoritative server gates: their local history remains, but trusted progress begins with the anonymous identity's server state. Offline cached completion may still appear in the UI; it cannot pass a server gate. This is a necessary trust-boundary change, not a silent import of editable local claims.

Before requesting deployment approval:

1. Use Node 24 and configure server-only `FIREBASE_SERVICE_ACCOUNT_JSON` or suitable Application Default Credentials with the required Auth/Firestore permissions. The target project/database come from the existing Firebase config; a JSON service account for another project is rejected. Do not place credentials in Vite variables or a committed file. Anonymous Auth must be enabled to support authenticated guest execution; otherwise users must sign in.
2. Run `npm run review:progress-migration` with explicitly supplied server credentials. This script only reads paginated user documents and prints aggregate compatibility counts, without learner data. It flags malformed arrays/maps, unknown current-topic IDs and documents over approximately 700 kB. It is not a backup or an automatic repair, and its reads consume existing Firestore usage. This production preflight has **not** been run in this revision.
3. Review flagged records and take an approved backup of users, histories and shared exams using your existing backup process. No backup service or export billing has been enabled by this change.
4. Stage and validate the new client/server together. Coordinate a short assessment-write maintenance window: restrict Firestore client writes before exposing trusted migration/progression endpoints, then publish the new client/server. Apply rules to the existing named database, not an unused default database. Leaving the new backend active while the old permissive rules remain deployed permits old clients to corrupt its backing state. Old clients will receive denied writes or 401s and must reload; a mixed-version window is not supported for assessment writes.
5. After approval and deployment, verify real token authentication, named-database IAM, owner-only reads, denied direct writes, quota sharing and a complete submission using disposable test accounts. The public health endpoint remains HTTP 200. Do not roll back by reopening client assessment writes.

The patched Firebase Admin/Firestore SDKs require a supported newer Node runtime, so `package.json` now declares Node 24 (already used by this repository's Vitest suite). The lockfile uses Firebase Admin 14.5.0, Firestore client 9.1.0 and a compatible patched gRPC 1.14.x override for the Firebase client. Production/service credentials and real provider authentication have not been exercised here.

## Tests and remaining limits

The local emulator script checks 61 denied operations across unauthenticated, owner, other-user and client-admin-claim contexts, preserves owner history reads, and checks real Admin SDK cross-instance transaction contention. It also verifies native Firestore timestamps survive archival. Run with a loopback emulator only: `firebase emulators:exec --only firestore --project demo-cplusplus-security --config firebase.security-test.json 'npm run test:firestore-security'`. Java and Firebase emulator tooling are required; temporary tools were used locally rather than adding deployment services.

Vitest adds authentication/revocation, forged progress/quiz/exam payloads, cross-user sessions, legacy markers/history, per-user/global quotas, spoofed headers/UIDs, replica coordination, lease expiry, store outages, idempotent exam writes and partial-grade retry coverage. Existing compiler, scoring, curriculum, readiness and migration regressions remain applicable. A built-server local HTTP check verifies public health and unauthenticated rejection on all seven protected entry points.

Final results: **230 Vitest tests pass**, **61 negative emulator rule checks pass**, real cross-instance Firestore concurrency and timestamp preservation pass, and TypeScript/build/bundle checks pass. The built API smoke check passes (public health 200, protected routes 401). Final `npm audit` reports **zero known advisories** for the resolved lockfile; this is not a guarantee of absence of vulnerabilities. The existing main-bundle size warning remains.

Remaining limitations are explicit: public teaching code/quiz keys and client-shipped exam pools are not confidential; this is not proctoring or protection against copying answers. Assistance flags, interview transcripts, manual reading completion, browser tab tracking and the displayed exam timer are learner/browser assertions. The server enforces session ownership and a 24-hour session retention/expiry window, not a new timed-exam disciplinary policy. Existing historical claims are grandfathered, not retroactively proved. API quotas bound expensive work but do not prevent all account farming, authentication/read-quota denial of service, or same-origin script compromise. App Check/WAF enforcement has not been configured.

Expired sessions and per-user quota documents are not automatically deleted; an approved administrative retention/cleanup process is still needed. Session expiry is an application check, not a configured Firestore TTL policy. Large existing root documents require review because Firestore's document-size limit still applies. There is no live production, real-credential browser or load-test result in this revision. No deployment or billing change occurred.
